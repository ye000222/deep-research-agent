Deep Research Agent 第二阶段开发计划
====================================

文档版本：V2.0-plan
制定时间：2026-08-31 22:25:05（Asia/Shanghai）
项目目录：D:\agentProject


一、阶段定位
------------

第二阶段的目标不是增加 Multi-Agent、PDF 或向量数据库，而是把当前“可运行、可演示的 V1 Alpha”提升为“可验证、可恢复、可由 GitHub CI 持续证明质量的严格 V1”。

本阶段围绕六个核心问题收口：

1. GitHub CI 能否在真实 PostgreSQL 环境中验证数据库、迁移、Outbox 和 Checkpoint？
2. Agent 能否明确记录现在知道什么、不知道什么、为什么继续或停止？
3. Memory 是否真正参与运行时检索、重验证、衰减和遗忘，而不只是保存历史文本？
4. Evaluation 是否能验证证据支持关系，而不只是统计引用数量？
5. Dynamic Planning 是否能根据 Gap 和信息增益修改研究计划？
6. 报告中的事实、分析结果和引用能否完整回溯到固定网页快照？


二、当前基线
------------

已经具备：

- FastAPI、React、Celery、Redis、PostgreSQL 18、SearXNG 和 Docker Compose 基础工程。
- OpenAI Responses、Anthropic Messages、Google Gemini、OpenAI-compatible Chat 四类模型协议。
- 加密保存模型配置和 API Key，Run 使用不可变模型配置快照。
- Planner、Research Loop、Web Search、Web Reader、Evidence Extractor、Report Writer 主链路。
- Evidence Graph、Context Budget Manager、Working/Episodic/Semantic Memory、Tool Policy。
- Research Coverage Map、Information Gain、停止预算、Markdown 报告和可点击引用。
- MyPy 98 个源文件 0 errors，Ruff 通过，Pytest 83 passed、2 skipped，前端构建通过。

当前主要缺口：

- PostgreSQL 集成测试仍依赖显式环境变量，GitHub CI 没有独立集成测试 Job。
- Evaluation 主要是 question-scope 确定性快照，缺少完整查询 API、LLM Critic 和语义支持验证。
- Memory Search Projection 已存在，但运行时 Memory Retrieval 仍以应用层词项匹配为主。
- Planner 主要生成初始计划，尚未形成受控的动态计划树和 REPLAN 闭环。
- Analysis Artifact 可以追溯到 Evidence，但 Writer 尚未自动生成分析引用。
- Checkpoint、Celery 重投、SSE 事件丢失和事务边界缺少真实 Failure Injection。
- Golden Eval 样本量过小，暂时不能证明 Release Gate 中的质量指标。


三、阶段边界
------------

第二阶段包含：

- GitHub Actions 真实 PostgreSQL/Redis 集成测试。
- Evaluation、Knowledge、Gap、Action、Verification 查询 API。
- Evidence/Question/Global/Section/Report 多层 Evaluation。
- LLM Critic 与确定性 Termination Judge 分层。
- 事实句与 Evidence Quote 的语义支持验证。
- Memory PostgreSQL Hybrid Runtime Retrieval。
- 跨任务“研究经验”型 Procedural Memory。
- Dynamic Planning、问题追加、计划版本和 REPLAN。
- Analysis Artifact 到 Report Citation 的自动生成链路。
- Provider Quick/Full Connection Test 与 Capability Matrix。
- Celery、Outbox、Checkpoint、SSE 和安全 Failure Injection。
- Golden Eval 扩充及前端解释性面板收口。

第二阶段不包含：

- Multi-Agent、Handoff 和多个 Researcher 并行协作。
- PDF、图片、音频、视频和上传文件。
- 任意 Python 或 Shell 执行。
- Embedding API、pgvector 或独立向量数据库。
- 登录网页、付费墙、验证码和浏览器自动化。
- 多租户权限、计费、团队协作和订阅系统。

五、详细任务
------------

S2-0：GitHub CI 与真实数据库基线
--------------------------------

目标：让远程 CI 不只执行内存/Mock 测试，而是在 PostgreSQL 18 和 Redis 上验证真实 Schema 与持久化路径。

开发内容：

- 为 GitHub Actions 增加 integration Job。
- 使用 PostgreSQL 18 Service Container，并创建 deep_research 与 deep_research_checkpoint 两个 Database。
- 安装 pg_trgm、unaccent Extension。
- 执行 Alembic upgrade head。
- 执行官方 AsyncPostgresSaver setup。
- 设置 RUN_POSTGRES_INTEGRATION=1，运行 PostgreSQL 集成测试。
- 将 test_postgres_recovery.py 从“脚本存在性检查”改为实际执行恢复探针。
- 增加 Evidence Projection、Memory Projection、Outbox 和 Agent Event 唯一序号检查。
- 将 Unit、Integration、Web、Compose 分为清晰的 CI Job。

测试用例：

- Profile 和加密 Credential 持久化后可读取脱敏视图。
- Run 与 Outbox 在同一事务创建。
- 迁移头必须为当前 Alembic Head。
- accepted Evidence 与当前 Retrieval Projection 数量一致。
- (run_id, run_seq) 无重复且严格递增。
- 事务回滚不残留测试数据。
- Checkpoint Database 能读写最小 Checkpoint。

验收标准：

- GitHub Actions integration Job 连续三次通过。
- 集成测试 Job 中 PostgreSQL 测试 0 skipped。
- CI 日志不出现明文 Secret、数据库密码或 API Key。
- CI 总耗时保持在可接受范围，目标不超过 10 分钟。

- test: execute real recovery and projection probes


S2-1：Evaluation、Knowledge、Gap、Action API
--------------------------------------------

目标：让前端和测试能够读取 Agent 的真实知识账本，而不是通过 Evidence 数量和事件摘要进行推测。

新增或补齐接口：

- GET /api/v1/research-runs/{id}/knowledge
- GET /api/v1/research-runs/{id}/gaps
- GET /api/v1/research-runs/{id}/actions
- GET /api/v1/research-runs/{id}/evaluations
- GET /api/v1/research-runs/{id}/verification
- GET /api/v1/research-runs/{id}/sources
- GET /api/v1/evidence/{evidence_id}

开发内容：

- 增加 Knowledge Snapshot、Gap、Action、Evaluation 的 Repository 查询。
- 返回稳定的分页、排序、状态和版本字段。
- 所有接口按 owner_hash 校验 Run 所有权。
- Evaluation 支持 evidence/question/global/section/report Scope。
- API 不返回完整 Prompt、模型隐藏推理、认证信息或网页全文。
- 前端 Known/Unknown/Next 改为真实 API 数据，不再使用近似统计。
- 增加 Evaluation 时间轴和决策原因展示。

验收标准：

- 每个 Known Claim 都能回溯到 accepted Evidence。
- 每个 Open Gap 都包含 Question、Dimension、Acceptance Criteria 和 Severity。
- 每个外部 Action 都绑定至少一个 Gap。
- Evaluation 指标可以回溯到 State Version 和 Scoring Rule Version。
- API 单元测试、所有权测试和 404/409 状态测试全部通过。

建议提交：

- feat: expose knowledge gap action and evaluation APIs
- feat: bind explainability panels to persisted state


S2-2：语义级 Report Verifier
-----------------------------

目标：验证“引用是否真正支持报告句子”，不只检查正文中是否存在 [1]。

验证流程：

报告事实句
  → 提取 Citation Marker
  → 查找 Claim/Evidence/Snapshot/Chunk
  → 检查 Exact Quote 存在性
  → 检查时间、地区、定义、单位和实体范围
  → LLM Critic 判断 supported / partial / unsupported / contradicted
  → 确定性规则决定保留、降级、删除或披露

开发内容：

- 增加 Fact Statement 分句与分类。
- 数字、日期、公司、产品和比较性断言强制进入验证。
- 设计 CitationSupportResult JSON Schema。
- LLM Critic 只能给出语义判断，不能修改 Evidence、预算和最终硬门槛。
- 对 Unsupported 句子最多执行一次引用修复。
- 修复失败的句子删除、降级或写入 Limitations。
- 保存 report-scope Evaluation Snapshot。
- verification_result 增加失败句、失败原因和 Evidence Ref。

验收标准：

- Citation ID 解析率 100%。
- 数字、日期、公司和产品事实引用率 100%。
- Golden Set 上 Evidence Support Precision 不低于 95%。
- 主题相关但不支持结论的 Citation 不得通过。
- Unsupported 核心事实不得出现在最终报告中。

建议提交：

- feat: add semantic citation support verifier
- test: add report entailment golden cases


S2-3：Memory PostgreSQL Hybrid Runtime Retrieval
------------------------------------------------

目标：让 Memory 真正通过版本化 PostgreSQL 检索投影参与 Agent 决策，并形成检索、重验证、衰减和遗忘闭环。

运行时检索流程：

Scope/Status/Expires 过滤
  → tsvector 词法召回
  → pg_trgm 模糊召回
  → RRF 融合
  → Confidence/Freshness/Importance/Utility 重排
  → MMR 去重
  → Top-K Memory Cards

开发内容：

- ResearchMemoryManager 改为查询 memory_search_documents。
- Evidence 和 Memory 状态变化时，在同一事务维护检索投影。
- 保留 rebuild_retrieval_projections.py 作为修复和版本升级工具。
- Query 与 Document 必须使用相同 Normalizer/Tokenizer Version。
- 跨任务 Memory 只返回 candidate lead，并设置 revalidation_required=true。
- 加入 Procedural Memory：保存有效 Query 模板、来源选择经验和失败规避经验。
- Procedural Memory 不保存未经证据支持的行业事实。
- 配置 Celery Beat 或独立 Scheduler 执行 Memory Lifecycle。
- stale/forgotten Memory 必须退出 Active 检索路径。

测试与评估：

- 中文、英文、混合中英文、年份、型号、百分比和货币查询。
- 中文 OOV、繁体词、1～2 字短 Query。
- 同一输入和 Retrieval Config 的 Top-K 顺序稳定。
- 跨任务 Memory 命中后不得直接成为当前 Citation。
- EXPLAIN (ANALYZE, BUFFERS) 验证 GIN/BTREE 索引。

验收标准：

- Candidate Recall@50：中英文分别不低于 0.90。
- NDCG@10：中英文分别不低于 0.80。
- Memory Recall@K 不低于 0.85。
- Memory Precision@K 不低于 0.80。
- active Memory 与当前 Retrieval Config 投影一一对应。
- 过期 Memory 直接成为新报告 Citation 的数量为 0。

建议提交：

- feat: use PostgreSQL hybrid retrieval for runtime memory
- feat: add procedural research memory lifecycle


S2-4：Dynamic Planning 与 REPLAN
--------------------------------

目标：让 Agent 根据当前 Knowledge、Gap 和信息增益修改计划，而不是只执行首次生成的固定问题列表。

触发条件：

- 发现用户目标中的新关键维度。
- 当前问题拆分后出现必须独立验证的子方向。
- Evidence Conflict 需要专门消解。
- 连续低信息增益说明当前 Query 路线无效。
- Memory 提供了高价值但尚未验证的新研究线索。

开发内容：

- Research Question 支持 parent_id、created_reason、plan_version 和 acceptance_criteria。
- 增加 plan.revised、plan.question_added、plan.question_updated 事件。
- Replan 候选由 LLM 提出，确定性 Policy 校验重复、预算、依赖和预期信息增益。
- 每轮最多新增 3 个问题，总问题数不超过 12。
- 新问题必须绑定触发它的 Gap 或 Conflict。
- Question Scheduler 按 Priority、Severity、Information Gain 和 Dependency 排序。
- 新计划写入后重新计算 Coverage Map。
- 前端用树形结构显示原始问题与动态问题。

验收标准：

- 固定“发现新维度”Fixture 能自动新增研究问题。
- 重复问题和同义问题不能进入计划。
- 新问题无 Acceptance Criteria 时必须被拒绝。
- Replan 不得突破问题数、迭代、搜索和 Token 预算。
- Checkpoint 恢复后不重复新增同一个问题。

建议提交：

- feat: add policy-gated dynamic research planning
- feat: visualize plan revisions and question lineage


S2-5：Analysis Artifact 到 Report Citation
-------------------------------------------

目标：让 CAGR、增长率、占比、排名和统计比较在报告中形成可重算的正式引用。

开发内容：

- Writer Context 中加入 Analysis Artifact Card。
- Report Paragraph 可以引用 Evidence ID 或 Analysis Artifact ID。
- Citation Registry 为 Analysis Artifact 分配稳定 Citation Number。
- Analysis Citation 记录 Operation、Formula Version、Parameters、Assumptions 和 Input Evidence IDs。
- 引用详情页展示公式、输入数据、单位转换和 Warning。
- Verifier 重新执行白名单 Operation 并比对结果。
- 计算不一致时禁止报告使用该分析结果。

验收标准：

- 每个 Analysis Artifact 关联全部输入 Evidence。
- 计算结果重算一致率 100%。
- 分析引用能够回溯到 Artifact、Claim、Evidence、Chunk 和 Snapshot。
- Writer 不得把没有 Artifact 的模型计算写入报告。

建议提交：

- feat: cite analysis artifacts in research reports
- test: verify deterministic analysis recomputation


S2-6：Provider Connection Test 与 Capability Matrix
---------------------------------------------------

目标：在开始研究前识别 Key、Model、协议和结构化输出能力问题，减少运行中途失败。

新增接口：

- GET /api/v1/llm/providers
- POST /api/v1/llm/connections/test
- POST /api/v1/llm/profiles/{id}/test

Quick Test：

- Base URL 与 TLS。
- 网络安全策略。
- 鉴权。
- Model ID 最小生成。
- Provider Request ID 和延迟。

Full Test：

- Structured Output。
- Synthetic Tool 或 AgentDecision 降级。
- Streaming。
- Usage Reporting。
- Context Window 和 Max Output。
- Reasoning Controls。

开发内容：

- 保存 Capability Matrix、Adapter Version、Model、Config Hash 和过期时间。
- Run 创建时固化 Capability Snapshot。
- 明确 native/emulated/unsupported/unknown。
- Capability 不足时在创建 Run 前失败。
- 前端增加“快速测试”和“完整能力测试”，提示可能产生少量费用。
- 错误区分 AUTH、MODEL_NOT_FOUND、PROTOCOL、TIMEOUT、CAPABILITY_INSUFFICIENT。

验收标准：

- 四类 Adapter 都有 Contract Test。
- 错误 Key、错误 Model、协议不兼容和能力不足可区分。
- Structured Output 失败时不得执行 Tool。
- Profile 修改不影响已经启动的 Run。
- API Response、日志和 SSE 中明文 Key 命中数为 0。

建议提交：

- feat: add provider capability probing
- feat: show connection capability matrix in settings


S2-7：Failure Injection 与安全加固
-----------------------------------

目标：证明长任务能在重复投递、Worker 崩溃、通知丢失和事务边界失败时安全恢复。

Failure Injection 场景：

- Celery 在 Tool 成功后、Ack 前崩溃并重复投递。
- Evidence 已提交但 Checkpoint 尚未写入。
- Checkpoint 已写入但下一业务事务失败。
- Outbox 数据已提交但 Broker 发布失败。
- Worker Lease 过期后由新 Worker 接管。
- Redis Pub/Sub 通知丢失。
- SSE 客户端断线后使用 Last-Event-ID 重连。
- Provider 请求超时、限流和网络断开。
- 单个网页读取失败。

Checkpoint 验证：

- Pending Writes。
- Time Travel。
- 最新 Checkpoint Resume。
- 显式旧 Checkpoint Replay。
- adelete_thread。
- 官方 Conformance Test。

安全测试：

- 私有 IP、Metadata Endpoint、DNS 解析私网地址。
- 跨 Host Redirect 不携带认证信息。
- URL userinfo、query 和 fragment 拒绝。
- Prompt Injection 网页 Fixture。
- API Key 在数据库、Redis、日志、Trace、SSE、Celery Payload 和前端存储中的泄漏扫描。

验收标准：

- 重复投递不重复 Evidence、Tool Call、Budget 或 Event。
- 用户取消后 5 秒内停止新的外部调用。
- 单页失败不终止整个研究任务。
- 恢复前后 Knowledge Fingerprint 一致。
- Secret 泄漏扫描结果为 0。
- SSRF 和跨 Host 认证泄漏测试全部通过。

建议提交：

- test: add celery checkpoint and outbox failure injection
- security: harden provider and reader network boundaries


S2-8：Golden Eval 与前端解释性收口
-----------------------------------

目标：用可重复数据证明 Agent 的 Gap、Action、Evidence Support 和 Stop Decision 达到预期，同时让用户能够理解每个关键决策。

Golden Eval 数据集至少覆盖：

- 证据充分。
- 无证据。
- 单来源。
- 多 URL 转载同一原始来源。
- 过期来源。
- 数值冲突。
- 时间、地区、单位和定义范围不一致。
- 搜索无结果。
- 网页读取失败。
- 连续重复 Query。
- 连续低信息增益。
- 预算耗尽。
- 动态新增问题。
- 引用存在但不支持句子。
- Analysis Artifact 计算错误。

前端收口：

- Known Claim 详情和 Evidence 链。
- Unknown Gap、Acceptance Criteria 和 Resolution Attempts。
- Next Action 的 Gap、信息增益、成本和 Policy Result。
- Context Item、Compression 和 Provenance 详情。
- Memory Hit/Miss、Scope、Score 和 Revalidation 状态。
- Evaluation Snapshot 时间轴。
- Conflict 左右证据对比。
- Analysis Artifact 公式与输入证据。
- Report Fact 到 Citation 的验证状态。

验收标准：

- Gap Recall 不低于 85%。
- Stop Decision 与人工标注一致率不低于 90%。
- Evidence Support Precision 不低于 95%。
- 错误提前停止率不高于 5%。
- 所有前端解释数据来自服务端事实源，不使用近似计数替代核心状态。

建议提交：

- eval: expand V1 research quality golden dataset
- feat: complete research explainability workspace

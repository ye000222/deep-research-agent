一、目标与判断口径
------------------
用户要求：提高研究覆盖率、降低耗时和 Token，同时保持准确率和研究成功率。本方案按当前代码设计，可逐项实施。
100% 执行进度表示流程已结束，不表示全部研究问题已满足；completed_with_limitations 必须单独统计。
外部来源和模型响应有不确定性，不能从几次通过推导“永不下降”。以版本化对照实验、明确质量门和可回滚开关控制风险；证据不足照实披露。

不可降低的验收要求：
1. Exact Quote 可定位到实际 Snapshot/Chunk；Snippet、历史报告、压缩摘要不能直接充当原文证据。
2. 保持现有事实支持、来源独立性、冲突披露、时效性和关键事实引用门槛。
3. 原始研究目标、验收维度和优先级不可为提高覆盖率而被静默删改。动态新增问题单独标识。
4. 预算预留、取消、任务重投、Secret、SSRF 和 Checkpoint 不变量继续通过。
5. 固定硬预算不自动增加；失败和重试消耗计入总成本；无法获取 Usage 标记 estimated，不能计成零。

拟定性能目标（实验目标，不是当前成果；全部相对冻结基线）：
- 同题同预算：Token 中位数减少 >=20%，端到端耗时中位数减少 >=20%，p95 不恶化。
- 加权覆盖率中位数提高 >=10 个百分点；基线已有高覆盖的任务不允许明显退步。
- 未尝试研究问题数下降；可执行且有预算的原始问题首轮触达率 100%。
- 引用支持精度不得低于基线，且不得低于现有发布门；关键事实缺引/错引不得新增。
- 技术完成率、质量达标率分别不得退步，禁止用更多带限制完成替代质量成功。
- 若某项优化只降低耗时而 Token 不变，可单独验收，不能宣称达到全部目标。

二、当前核查结果与上轮结论修正
----------------------------
已直接检查文件：
- apps/api/app/infrastructure/db/research_tools.py
- apps/api/app/services/research_loop.py
- apps/api/app/services/evidence_extractor.py
- apps/api/app/services/report_writer.py

观察到的事实：
1. evidence_model_budget 使用剩余 Token 减 Writer 预留，再减 (pending_questions-1)*3000；不足时仍设置全局 model_budget_guarded。
2. pending 统计包含 blocked/partial/technical_retry，未按已耗尽尝试次数过滤；方法没有当前 question_id 参数。
3. 因而这只是算术预留，没有“本题让出预算→切换下一题”的调度闭环。未完成数不减少时，预留可以导致更早全局结束。
   示例：剩余 22,000，Writer 预留 10,000，未完成 5 题，available=0；仍有 12,000 研究额度，却会全局停止。
4. 3,000 调用额度在 Extractor 中会使 output_tokens 至多约 1,000，并压缩 input cap；上轮“只改门槛、不影响输出”表述不充分，需按真实请求预算验证。
5. Extractor 按每 3,000 字符分块，rank_score 按网页位置递减；无 Context Manager 时只取前 14,000 字符。后部相关证据可能遗漏。
6. research_loop 当前逐网页读取、抽取，一轮申请最多 3 个页面槽位。存在网络等待优化空间，但并发必须建立在原子预算和幂等上。
7. Writer 有自己的预算判断；研究侧与写作侧应统一消费账本和调用预算定义，避免预留口径分歧。

不能从现有证据确认的事项：
- 最近几次实测的具体 Token 分布、失败重试占比、网页选择损失，需要读取脱敏 Run 指标后测量。
- 上轮 Strict Gate 未全过：缺少测试数据库环境；不能将通过的单元测试等同于真实数据库/Provider 验证。
- 本轮未执行性能实验；下文数值均为初始参数或验收目标。

A. 固定网页+固定 Provider 响应回放：至少 30 个案例，验证确定性调度、引用、预算和恢复；不能称为真实互联网成功率。
B. 同一 Provider 配置的真实运行：先 3 例冒烟，再至少 30 题各版本重复 3 次，交替运行旧/新版本，记录服务错误率和时间窗口。首次批量真实调用须确认成本上限。

固定原始问题权重分母，原始与动态 Coverage 分开；统计每题触达/有效证据/未解决原因。
输出按样本成对比较的 JSON 和可读摘要；按研究题目聚类计算 95% 区间，不能把同一题重复运行当独立题目。
零退步门：准确率和两种成功率的差值区间下界需 >=0 才可严格声称不退步；样本不足以判定则扩大样本或保持实验开关关闭，不能以“未显著变差”等同“证明相同”。
现有 Golden 绝对门槛同时保留；人工盲评固定抽样报告的全部关键事实，至少抽查 100 条事实。
失败任务也进入耗时/成本统计，另报成功任务性能，防止快速失败制造提速。

四、P1：预算与问题调度闭环（最高优先级，预计 2～3 日）
-------------------------------------------------
改动：db/research_tools.py 的 evidence_model_budget/prepare_target/finish_iteration、services/research_loop.py、domain/research_management.py、report_writer.py。
新增纯领域策略模块：domain/research_budget.py。预算判定独立于网络，可直接测试。

接口草案：
BudgetDecision { outcome: execute|yield_question|stop_run,
  question_id, input_limit, output_limit, repair_reserve,
  writer_reserve, future_question_reserve, reason }
evidence_model_budget 必须接收当前 question_id/action_id；调用者按 outcome 分支，不能用 allowed=False 统一终止。

预算定义：
research_available = hard_limit - actual_spent - active_reservations - writer_reserve
最低调用成本 = 实际装配的 instructions + task + schema + 至少一个可用原文片段 Token + 输出预留 + 估算安全余量。
按实际 Provider tokenizer/保守估算计算，不再假定 3,000 对所有模型和任务都够。
Writer reserve 来自拟写章节、待引用证据和输出预算；必须有上限且保持与 Writer 实际请求一致。小预算时先完成可行性检查。

实施顺序：
1. 引入未研究、已尝试、部分支持、已完成、依赖暂不可用、尝试耗尽的调度属性；依赖失败不算无证据。
2. 尚未尝试的原始问题先获得一次可执行机会；同组按用户优先级与等待时间排序。第一轮每题最多一个有效页面抽取，然后轮转。
3. 首轮覆盖之后按预期“新增被支持的验收维度/预计 Token 与耗时”分配追加调用，同时用等待轮次防饿死。
4. 当前问题不能动用其他问题保留额度时返回 yield_question；不设置 model_budget_guarded，不增加质量失败次数，不把问题标红为证据失败。
5. 下一次 prepare_target 跳过本轮已让出的相同候选，避免忙循环；扫描一圈无人能执行才 stop_run，并列出未尝试原因。
6. 仅当任一合法研究调用都不可支付或硬期限触发时设置全局 stop。预留不足可按优先级显式分配可支付席位，不能虚构所有题都有 3,000 可花。
7. 已耗尽尝试、已完成与长期等待依赖的问题不持续锁死可用预算；等待恢复保留状态但释放未实际执行的调用预留。
8. 一轮完成后基于实际消耗重算；新问题进入前验证预算，不静默替换原始问题。

持久化拟定：model_budget_reservations 表，UUID id、run/action/logical_call/attempt、estimated_input、max_output、reserved_total、actual_total、status、lease_until、created_at/settled_at。
唯一键 (run_id, attempt_id)；状态 reserved→settled/released/uncertain。锁 Run 并检查总额度后预留，网络调用在事务外，结果回写幂等结算。
Provider 超时且可能已处理：预留转 uncertain，不能直接退还成零；按保守上界占用，后续对账。Worker 崩溃后同理。
业务结算与事件原子落库；Checkpoint 重放不能再次扣同一个 attempt；新一次 Provider 请求必须有新 attempt。
Migration 从运行时 head 派生，新文件序号先读取实际 Alembic head，禁止写死本文件猜测版本。

必须补测：22k/5题反例；当前题让出后下一题执行；blocked 尝试耗尽释放额度；两 Worker 争抢不得越界；重复结算；超时未知 Usage；恢复不重复扣款；全部题不可支付正确终止；首轮轮转不丢高优先级。
完成条件：预算可行的回放案例不存在最后若干题从未尝试；引用规则不变；真实总花费在硬预算及明确估算误差策略内。

五、P2：按证据相关性装配上下文（预计 2～3 日）
-------------------------------------------
改动：evidence_extractor.py、context/manager.py；新增 context/source_selector.py 和后部证据 Fixture。
1. 正文按段落/标题/表格边界切块，保留 snapshot_id、chunk_id、原文字符偏移、content_hash。
2. 以当前问题和未满足 acceptance dimensions 检索全文块；使用既有中英分词与词项检索，数值、型号、实体保留精确匹配。
3. 按相关度和维度缺口排序，再做 MMR 去重；每个尚未满足维度尽量分到原文空间，保留邻接段落和表头，最后按原文顺序呈现选中块。
4. 第一遍小上下文；候选没有证据、维度遗漏或来源截断时，扩大相关块/邻接块继续抽取；不能将“未选中”解释成“网页不存在”。
5. 仅发送新块与必要任务指令，不重复装入整个历史。扩展次数最多一次作为初值，后续不足返回明确 Gap。
6. exact_quote 必须从原始正文定位。摘要只服务导航，不可作为引文来源；不拼接不连续文本制造支持。
7. 输入压缩优先于砍输出。根据拟返回 1/3/5 条 Evidence 选择独立 Schema 上限；预算不足时明确使用小批次 contract，禁止保持五条大输出要求却任意压到 1,000 Token。
8. 动态 Schema、输入加输出、repair 都由 P1 预算支付；格式失败按错误类型修复，避免重复整页。

初始可调参数：上下文 3k→6k 两档，MMR lambda=0.7；这些参数需 Golden 调优，不能直接替换生产默认。
验收：前部/后部/中英/跨段否定/日期条件/表格均可召回原文；关键证据 Recall 不低于全文基线；扩展费用计入净节省；模型错误率不增加。

六、P3：减少重复工作，提高有效覆盖（预计 2～3 日）
--------------------------------------------
改动：research_loop.py、db/research_tools.py、artifacts.py、memory/manager.py；按需要新增 extraction_cache 表。

三层缓存必须分开：
A. 网页 Snapshot：同 Run、相同 URL/正文哈希可复用已读正文；跨任务要检查新鲜度并重验证。建议普通网页 TTL 初值 24h、时效性事实强制重取，参数需按任务时间约束覆盖。
B. 抽取结果：键包含 scope、snapshot_hash、question/维度哈希、model/adapter/config、prompt/schema/extractor 版本。只缓存成功且原文校验通过的结果；空结果不等价于网络/格式失败。
C. 证据到维度的映射：同一事实支持多个维度时分别建立支持关系、验证语义；相同来源不增加独立 Owner 数。不把某题 cache hit 当作其他问题已完成。

缓存命中重新运行当前证据接纳规则；跨任务 Memory 仍只提供线索和研究经验。API Key 不参与明文缓存键，隔离依据 owner/scope/credential handle 版本。
来源筛选按相关性、可读性、原始出处、缺失维度、独立 Owner 排序。近重复转载降低选择优先级；唯一来源不能因去重算法误删。
搜索按 Gap 缺失内容生成中英文/实体/官方出处候选；保留搜索新配额给尚未触达问题，避免重复同义搜索。
完成条件：相同 Snapshot+问题不重复模型抽取；不同问题仍正常搜索；过期/版本变化缓存失效；多维证据 Coverage 无虚增。

Deep Research Agent V1 第三阶段规划
===================================

文档名称：第三阶段.txt
阶段名称：V1.1 稳定性、可观测性与质量工程
生成时间：2026-09-02 13:02:45
规划依据：当前项目代码、测试、Docker 运行状态、GitHub CI 状态及 V1 功能审查结果

一、阶段目标
------------

V1 主功能已经形成完整闭环：研究计划、搜索、网页读取、证据提取、Evidence Graph、Coverage Map、Context Budget、Memory、动态 REPLAN、Evaluation、Verification、报告引用和进度可视化均已具备。

第三阶段不优先扩展 PDF、多模态、Embedding 或 Multi-Agent，而是把当前实现固化为可重复、可诊断、可度量的 V1.1 稳定版本。

本阶段最终目标：

- 代码、数据库 Migration、Docker 和 GitHub CI 可重复构建
- 测试数据库与开发数据库完全隔离
- Worker 崩溃、Lease 过期和 Celery 重投不会制造僵尸任务或重复副作用
- 每次 LLM 调用均可审计，但不泄露 Prompt、API Key 或原始敏感响应
- 研究启动前即可知道 Provider、Model 和 JSON/Tool 能力是否可用
- 通过真实端到端 Golden Benchmark 验证 Coverage、Citation 和 Stop Decision
- 失败任务能够解释失败阶段、失败原因和是否可以恢复
- 完成 V1.1 Release Gate 并发布 v1.1.0

二、当前审查结论
----------------

1. 代码与发布状态

- 当前工作区仍有一批未提交修改，包括进度可视化、长 URL 修复、兼容模型 JSON 修复和新的数据库 Migration。
- 已发布的 v1.0.0 不等于当前工作区的最新实现，必须先完成一次发布基线固化。
- [scripts/release_gate.py] 当前仍固定检查旧 Migration 版本，实际数据库已进入 20260902_0017，Release Gate 应改为动态读取并校验最新 head。

2. 任务生命周期

- 开发数据库中存在大量历史 running、interrupted 和 failed 任务。
- 部分 running 任务来自集成测试，Worker Lease 已过期但没有被统一回收。
- 测试数据污染开发数据库会导致前端任务统计、运行状态和故障判断失真。

3. 模型诊断能力

- Provider Adapter 已有基础降级逻辑，但运行时缺少完整的 LLM Call 审计链。
- finish_reason、尝试次数、降级策略、Provider Request ID、延迟和输出 Hash 尚未形成稳定的持久化记录。
- 兼容模型的 JSON 输出问题往往只能在研究运行后暴露，缺少启动前 Capability Test。

4. 质量验证

- 当前单元测试、API 测试和集成测试覆盖了主要结构，但真实 Provider 和真实端到端研究样本仍需扩大。
- 需要建立至少 30 个固定 Golden Case，分别评估中文、英文、来源稀缺、冲突来源、Prompt Injection 和模型降级场景。

三、任务分解与推荐顺序
----------------------

### S3-0：固化最新发布基线

工作内容：

- 建立 `codex/v1.1-stability` 分支。
- 盘点当前所有未提交修改，确认每项修改属于 V1.1 范围后统一提交。
- 更新 Release Gate，动态读取 Alembic 当前 head，不再硬编码 0016。
- 校验代码 Migration head、运行数据库 head 和 CI 使用的 head 一致。
- 确认 `启动操作.txt` 是否纳入仓库。
- 运行完整本地检查、Strict V1 Release Gate 和 GitHub CI。

验收标准：

- 工作区干净，变更均有明确 Commit。
- 最新 Migration 为 20260902_0017，且 Release Gate 能自动识别未来新增 head。
- 五项 GitHub CI 检查全部通过。
- V1.0.0 数据库能够升级到当前版本。

### S3-1：测试数据库隔离与任务生命周期修复

工作内容：

- 为集成测试使用独立 PostgreSQL Database 或独立 Schema。
- 测试结束后清理 Run、Event、Evidence、Checkpoint 和 Outbox 数据。
- 增加 stale-run reconciler，扫描过期 Worker Lease。
- 将过期 running 任务转为 interrupted/recoverable，避免永久停留。
- API/Worker 启动时执行轻量恢复扫描。
- 增加 Worker 被终止、Redis 重投、Lease 过期和恢复失败测试。

验收标准：

- 集成测试不污染开发数据库。
- 测试完成后残留业务任务为 0。
- 超过 Lease 时间的 running 任务为 0。
- Worker 崩溃恢复后不重复保存 Evidence、扣减预算或写入重复事件。

### S3-2：LLM 调用可观测性

工作内容：

- 增加 `llm_calls` 持久化记录。
- 记录 Run、Action、Node、Role、Adapter、Endpoint Host 和 Model。
- 记录 Structured Output 策略、Tool Calling 策略、尝试次数和降级路径。
- 记录 Provider Request ID、finish_reason、延迟、Token 用量和 estimated 标记。
- 记录返回字符数、脱敏内容 Hash、稳定错误码和脱敏错误摘要。
- 在研究工作台增加模型调用诊断面板。

禁止保存：

- API Key、Authorization Header。
- 完整 Prompt、隐藏推理和未脱敏 Provider 原始响应。

验收标准：

- 每一次模型调用都有审计记录。
- `MODEL_OUTPUT_INVALID` 能定位到具体尝试、策略和终止原因。
- Secret 泄漏扫描结果为 0。
- 不因增加审计而把敏感内容写入日志、SSE、Celery 或浏览器存储。

### S3-3：真实 Provider 能力测试

工作内容：

- 实现 `POST /api/v1/llm/connections/test`。
- 实现 `POST /api/v1/llm/profiles/{id}/test`。
- Quick Test 检查 URL、TLS、鉴权、Model、最小生成、延迟和 Request ID。
- Full Test 检查 Native JSON Schema、JSON Mode、Prompt JSON 降级、Tool Calling、Streaming、Usage、Context Window 和最大输出。
- 将能力测试结果写入 Capability Snapshot，并在创建 Run 时固化。
- 为 OpenAI Responses、Anthropic Messages、Google Gemini 和 OpenAI-compatible Chat 建立独立契约测试。

验收标准：

- 错误 Key、错误 Model、错误协议、网络错误和能力不足可以准确区分。
- 兼容模型在研究启动前即可确定 JSON 和 Tool Calling 策略。
- 能力不足时任务被明确拒绝，不运行到 Planner 才失败。
- Live Smoke Test 与 CI Mock Test 分离，避免外部费用和网络波动影响确定性测试。

### S3-4：真实端到端质量基准

建立至少 30 个固定 Golden Case，覆盖：

- 中文和英文研究问题。
- 技术路线、厂商产品、市场规模、趋势预测和数据集。
- 来源稀缺、网页不可访问和来源相互冲突。
- Prompt Injection 页面。
- JSON 输出异常、Provider 超时和有限重试。
- 动态追加问题和 Analysis Artifact 引用。

每个案例记录：

- 任务完成状态和 Stop Reason。
- accepted Evidence 数量。
- Global Coverage 和 Priority 1 Coverage。
- 来源质量、独立性、多样性和新鲜度。
- Citation Completeness、Citation Support 和关键事实可追溯率。
- 墙钟时间、Token、LLM 调用次数和 Provider 错误率。
- 无证据报告数量、僵尸任务数量和重复副作用数量。

建议目标：

- 可访问来源案例完成率不低于 90%。
- Priority 1 问题覆盖率不低于 80%。
- 关键事实 Citation Support 达到 100%。
- 数字和日期引用率达到 100%。
- Golden Set 的 Stop Decision 一致率不低于 90%。
- Secret、SSRF、Prompt Injection 逃逸数量为 0。

### S3-5：基于基准的研究质量调优

只根据 S3-4 的失败数据调整：

- Query 改写、同义词扩展和重复 Query 识别。
- 来源类型、Owner 独立性和转载去重。
- 高价值候选网页优先级。
- 每个问题的自适应预算与信息增益阈值。
- 连续低收益轮次和停止条件。
- Planner、Extractor、Evaluator 的重试、降级和错误边界。
- 冲突、新鲜度和来源不足的专项搜索。
- 报告写作前的 Evidence 缺口修复。

验收标准：

- 调优前后使用同一 Golden Set 对比。
- Coverage 提升不能以 Citation Support 或来源独立性下降为代价。
- 不允许通过放宽 Evidence 校验来人为提高覆盖率。

### S3-6：前端诊断与进度语义完善

工作内容：

- 展示当前阶段、当前问题、已用预算和预计剩余阶段。
- 展示最近一次成功动作、当前失败动作和重试倒计时。
- 展示 Provider/Model 当前状态及 Capability Snapshot。
- 对可恢复失败提供“恢复研究”按钮。
- 失败任务显示实际停止阶段和百分比，不伪装成 100%。

进度规则：

- `completed`、`completed_with_limitations`：100%。
- `failed`：保持失败时的实际百分比并标红。
- `interrupted`：保持当前百分比并标记可恢复。
- `cancelled`：显示取消时的实际百分比。

### S3-7：发布 V1.1.0

发布前必须同时满足：

- 连续三次 GitHub CI 全绿。
- V1.0.0 数据库升级测试通过。
- 真实 Provider Smoke Test 通过。
- 30 个端到端案例达到质量门槛。
- 过期 running 任务数量为 0。
- Release Gate 能动态验证最新 Migration。
- Secret、SSRF、Prompt Injection 测试全部通过。
- 进度文档记录最终 Release Gate 结果和完成时间。
- 发布 Git Tag `v1.1.0` 和 GitHub Release。

### 2026-09-02 13:27:21：Evidence Extractor 零证据热修复已完成

完成内容：

- Evidence Extractor 最大输出预算由 2,400 Token 提高到 6,000 Token，降低兼容推理模型在最终 JSON 完成前被截断的风险。
- 完整证据抽取经过 Adapter 内置 JSON 修复后仍失败时，新增“相关性最高的两个网页片段 + 最多 1～2 条 Evidence”的紧凑补救抽取。
- 对相关网页返回合法空 `items` 的情况增加一次受控紧凑重试；补救失败时保留原空结果，不把合法空结果错误升级为系统故障。
- 新增 Extractor 结构化输出熔断：同一研究问题连续两个来源在全部补救后仍无法返回结构化 Evidence，任务以 `MODEL_CAPABILITY_INSUFFICIENT` 明确失败，不再继续消耗全部搜索预算并最终误报 `REPORT_NO_ACCEPTED_EVIDENCE`。
- Adapter 开始归一化 `finish_reason`，结构化解析失败时生成不含原文的安全诊断码，包含输出策略、终止原因和响应字符数。
- `evidence.failed` 事件增加安全 `detail_code`，便于区分输出截断、Prompt JSON 失败和其他兼容问题。
- 新增 JSON 紧凑补救、空结果补救、连续失败熔断和安全 finish diagnostics 回归测试。

### 2026-09-02 22:26:35：Planner 结构化输出与失败进度语义加固已完成

完成内容：

- Planner 控制类生成参数固定为 `temperature=0.0`，OpenAI-compatible Adapter 不再使用硬编码 0.2，而是读取 Canonical Request 的温度设置。
- 保留 Planner 6,000 Token 输出上限；首次返回 `finish_reason=length/max_tokens` 时，第二次仍使用可用 JSON Mode，并要求显著压缩字段和数组后完整闭合 JSON。
- 结构化输出错误已拆分为 `MODEL_OUTPUT_TRUNCATED`、`MODEL_OUTPUT_INVALID` 与 `MODEL_OUTPUT_SCHEMA_INVALID`。
- JSON 解析诊断新增空响应、疑似截断对象、尾逗号、解码错误类型和字符位置；Schema 诊断记录 strategy、finish_reason 与安全的 Pydantic issue type，不记录模型正文、完整 Prompt 或 Secret。
- 最终 `run.failed` 事件继续保存安全 `detail_code`；前端根据 `FINISH_LENGTH`、`PROMPT_JSON`、`SCHEMA_INVALID` 显示针对性说明。
- `REPORT_NO_ACCEPTED_EVIDENCE` 事件新增失败阶段、搜索次数、读取页数和零 accepted Evidence 指标，明确这是 Evidence Evaluation 失败而非 Writer 自身故障。
- 失败任务不再把 `terminal` 机械映射为最终核验 96%；Planner 失败显示在“研究计划”，Extractor/模型能力失败显示在“搜索与阅读”，零证据失败显示在“证据评估”，失败阶段和进度条使用红色状态。
- 终态页面优先显示真实失败说明，不再被最后一条历史 action 事件覆盖。

### 2026-09-02 22:56:33：有界最小 Planner 与独立紧凑重答已完成

完成内容：

- Planner 不再直接要求模型生成完整 `ResearchPlan`；新增有界 `ResearchPlanDraft`，模型只生成研究范围、问题内容与完成条件。
- `goal` 直接使用任务的不可变研究目标，问题 `id` 由服务端按 `q1`～`qN` 确定性生成，减少 Token 消耗并消除目标改写、ID 重复和 ID 格式错误。
- 正常计划限制为 5～8 个问题，并对 scope、question、rationale、evidence requirements、search hints 和 completion criteria 分别施加字段长度与数组数量上限。
- 正常 Planner 的硬输出上限调整为 4,000 Token；核心策略是控制输出内容预算，而不是依赖不断提高 Token 上限。
- 首次发生长度截断、非法 JSON 或 Schema 不合法时，不再原样重答；第二次切换独立 `CompactResearchPlanDraft`：恰好 5 个问题、极短 rationale、每题恰好 1 条证据要求、最多 1 条搜索提示、恰好 2 条完成条件，输出上限为 1,200 Token。
- Planner 最多执行两次模型生成；紧凑计划仍被截断时返回明确的 `PLAN_OUTPUT_BUDGET_EXCEEDED`，不再用笼统的“模型不支持 JSON”掩盖原因。
- 结构化输出诊断记录 strategy、finish_reason、output/max tokens、response length、provider request id 和 retry mode；只将白名单安全字段写入 `run.failed` 事件，不记录模型正文、完整 Prompt、认证信息或 Secret。
- 前端失败区域显示结构化输出策略、终止原因、输出 Token 与上限、重答模式，并将 `PLAN_OUTPUT_BUDGET_EXCEEDED` 定位到“研究计划”阶段。

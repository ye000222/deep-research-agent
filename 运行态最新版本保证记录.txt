## 目的

从本记录开始，每次代码或运行配置发生改动后，必须同步更新实际运行态，不能只完成源码修改就直接交付测试。

## 固定执行流程

1. 运行 `docker compose up -d --force-recreate api worker dispatcher beat web`，重建所有会加载项目代码的服务。
2. 运行 `docker compose ps`，确认 API、Worker、Dispatcher、Beat、Web 均处于 `Up` 状态。
3. 检查 Worker 启动参数和日志，确认新配置已生效（当前并发配置为 2）。
4. 检查 Web `http://localhost:5174` 与 API `http://localhost:8000/openapi.json` 均返回 HTTP 200。
5. 对关键改动做容器内源码核验，避免宿主机文件已更新但容器仍使用旧版本。
6. 代码改动完成后再执行测试；只有“测试通过 + 运行态更新 + 健康检查通过”才算可测试版本。

## 2026-09-11 Run 01a08f12 终止原因诊断

### 已确认事实

- 终止状态：`completed_with_limitations`。
- 数据库终止分支：`sources_exhausted`，不是 `research_budget_exhausted`。
- 研究预算仍有余量：研究轮次 4/20、搜索 8/20、页面 4/30、模型 Token 8,913/100,000。
- 质量仍未达标：Coverage 11.11%，关键缺口 3，未回答问题 7；截图中的低增益连续次数为 21。
- 计划版本已到 3；q1、q2、q3、q5、q6、q7、q8 均为 `blocked`，只有 q4 获得 5 条证据。
- 每个缺口的 `resolution_attempts` 达到当前硬上限 3 后，`prepare_target()` 不再把它列为候选；候选为空时直接调用 `_enter_writing(..., reason="sources_exhausted")`。
- 32 次评估中有 24 次只是复用候选，实际搜索 8 次；13 个网页读取/提取失败，失败来源包含抖音、哔哩哔哩、人人文档、Docin、360 搜索结果页等不可稳定读取页面。

### 根因链路

1. 搜索结果中不可读取、动态渲染或文档站页面比例较高，导致网页读取/正文提取失败。
2. 候选复用机制正确地跳过已失败 URL，但没有足够的新鲜、可验证来源补位；多个问题连续产生 0 条新证据。
3. 这些问题的缺口重试次数达到 3 次后被硬性排除；计划版本 3 又禁止继续 Replan。
4. 于是“预算还有很多”与“当前计划没有可执行候选”同时成立，系统按 `sources_exhausted` 进入限制性报告，最终显示 `completed_with_limitations`。

### 结论

这次显示该状态是“候选/缺口状态机提前耗尽”，不是资源预算真的用完。当前最需要根治的是：在仍有搜索、页面和 Token 预算时，不能把缺口重试上限当作全局终止条件；应触发新查询策略/来源类型降级，并保留可执行候选，只有真实预算耗尽或明确不可恢复的技术故障才进入限制性写作。
